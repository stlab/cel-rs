# v1.0 milestone plan

Reviewed on 2026-11-03 for developers embedding Adam in their own Rust application
frameworks. V1 must let you drive UI behavior and capture changed source values
for recording and playback, similar to Photoshop Actions. This plan defines the
release gates, reconciles remaining handoff work, and records the disposition of
the open backlog. The historical work groups remain as implementation provenance.

Capture/playback scope was settled on 2026-11-04. PR #277 implements the agreed
effective-value snapshot contract and remains under review; it is not a merged
release-gate completion.

## V1 outcome and scope

A consumer application must be able to construct an Adam model, bind its own
controls, submit edits, propagate constraints, and update presentation and
validation state through public APIs. It must also be able to capture effective
source values and replay them against a compatible fresh model with matching
uncaptured context. The recording is a current-value snapshot, not an editable-state
checkpoint: preserving original aspirations, priority history, or behavior under
subsequent edits is outside the capture contract.

The supported host boundary is Rust. Foreign-language bindings are deferred.
Neither Begin nor EZ Adam is the required application framework, and their full
development environments are not release prerequisites. V1 does not require
language generics, inferred equations, capturing closures, exhaustive model
checking, a recording editor, or a prescribed application recording format.

The user approved the initial scope and corresponding GitHub updates on
2026-11-03, then clarified the snapshot boundary on 2026-11-04. The
[v1.0 milestone](https://github.com/stlab/cel-rs/milestone/1) had 13 open issues
immediately after the initial reconciliation.

### Capture and playback contract

PR #277 implements #271 as a framework-neutral iterator, not a recorder or a
serializer. The agreed contract has these boundaries:

- Capture after successful propagation and before further edits.
  `Sheet::source_cells()` includes unclaimed cells and selected self-referencing
  inputs, excludes pure derived outputs and `Out` cells, and allocates no storage.
  `is_source()` alone misses self-referencing inputs.
- Record effective `read<T>()` values, not the aspirations returned by `source()`.
  The result is a dictionary of final input values, not an explicit-edit journal.
  `changed()` remains a propagation-update query, not an equality comparison or
  a capture-consumption API.
- Let the client establish its baseline after construction, compare values,
  filter irrelevant or contextual inputs, and choose its recording format.
  Any omitted input becomes part of the context that must match during replay.
- Use host-defined names or schema keys across reconstruction, not live `CellId`
  values. The client knows the types of its recorded cells and owns checked codecs
  for built-in, compound, and registered host values. No serialization trait needs
  to pass through runtime type erasure.
- Write all captured values in any order as one batch before propagation.
  For a settled solution satisfying its relationships and filters, semantic
  relationship consistency and idempotence make the recorded solution a fixed
  point on a compatible sheet with matching uncaptured inputs. Different write
  priorities may select different methods without changing the effective result;
  strengths and write history need not be recorded.
- Do not promise identical original aspirations, priority history, diagnostics,
  or subsequent-edit behavior, including spring-back. These are not part of a
  current-value snapshot.

The public contracts live in `adam-rs/src/lib.rs`,
`adam-rs/src/relationship.rs`, and `Sheet::source_cells()` in
`adam-rs/src/sheet.rs`. Five contract tests in
`adam-rs/tests/contract_regressions.rs` cover classification, non-`Clone` host
values, shadowed final values, all six batch-write orders for inequality and
filter/conditional fixtures, same-value priority changes, and discarded
spring-back history.

#273 still makes the commit boundary consumable by hosts: explicit source writes
precede propagation, and some requirement callback errors occur after values
commit. A host must not treat every `Err` as a rolled-back action. #219 audits
residual aspiration/priority behavior during subsequent edits; it does not add
priority metadata to the snapshot contract.

### Implementation order

Use #271's agreed snapshot contract and PR #277 for the recording adapter.
Complete review and merge before closing the capture gate. Coordinate #273 and
the residual #219 contract with the adapter's error handling and later edits;
neither changes the decision to omit priority history from value capture.
Complete #186's remaining general solver fixture alongside that work. Existing
geometry demonstrations do not substitute for the issue's full
spring-back/reversal acceptance.

Develop #274 and #239 as a nonexecuting tooling track. Coordinate #258 and #259
before source-breaking changes; #155 and #175 belong to the same correctness
track. Do not implement #239 by constructing a live sheet inside the editor.

Build #272 against the agreed public contracts, then use its consumer fixture
for #275. #246/#270 are delivered independently of that host adapter. Run the
final integrated release gate after these tracks converge, not a full release
build after each planning or documentation change.
