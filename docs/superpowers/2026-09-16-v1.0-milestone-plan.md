# v1.0 Milestone — Independent Work Groups

Status snapshot as of 2026-09-16. This organizes the 12 open issues currently in the `v1.0`
milestone into groups that can be worked on independently (each group in its own worktree/PR
sequence) with minimal expected merge conflict, and orders the groups so that anything other
groups build on lands first. Within a group, issues are listed in the order they should land
if the group's issues touch overlapping code (noted per group); across groups with no listed
dependency, the groups themselves can proceed in parallel.

Gaps found in `docs/VISION.md`'s roadmap that had no tracking issue were opened separately
during this review: #218 (query pinned cells), #219 (cell "memory"/unlink behavior), and #220
(view-constraint sheets, blocked on #109/#110/#111). They are not v1.0-milestoned and are not
included in the groups below.

## Group 1 — adam-rs planner cleanup (do first)

**Issues:** #187 (Planner cleanup: adopt Kahn's topological sort, prune the acyclic search,
factor `propagate()` duplication)

**Why first:** #187 touches every file Group 2's issues also touch
(`planner.rs`, `matching.rs`, `release.rs`, `digraph.rs`, `scc.rs`, `seed.rs`, and `sheet.rs`'s
`propagate()`/`execute_plan`) and is a net-negative-line structural cleanup (deleting `scc.rs`,
standardizing on Kahn's/a DFS cycle check). Landing it before Group 2's functional changes
avoids those changes being written against, and then needing rebasing off, machinery this issue
deletes or restructures.

## Group 2 — adam-rs planner functional generalizations (depends on Group 1)

**Issues, in landing order:** #18 (Ensure planning only happens if a cell priority of a
non-source is raised) → #153 (Generalize `release::resolve` to search around filter-induced
cycles) → #186 (Generalize seedfill beyond self-referencing chains)

**Why grouped/sequential:** all three modify the same planner core (`planner.rs`, `release.rs`,
`matching.rs`, `digraph.rs`, `seed.rs`) that Group 1 cleans up first. They cannot be worked
fully in parallel with each other without high conflict risk, so treat them as one sequential
track rather than three independent groups. Suggested order: #18 is the narrowest (replanning
trigger condition); #153 builds on `matching.rs`/`release.rs` next (filter-cycle-aware
assignment search); #186 is the most involved (sibling-ordering and cycle-handling design work
per its own acceptance criteria) and benefits from #153's more complete `resolve()` first.

## Group 3 — adam-rs requirement identity + begin diagnostics wiring (depends on Group 1)

**Issues, in landing order:** #194 (adam-rs: track requirement names externally, report
violations by `RequirementId`) → #191 (begin: thread `method_spans` through the live Dioxus UI
for `write_and_propagate`)

**Why grouped/sequential:** both touch `adam-web-ui/src/inspector.rs` (#194 removes
`invalid_output_requirement_names` in favor of a caller-owned id→name table; #191 threads a new
`Signal<HashMap<(RelationshipId, usize), SourceSpan>>` through the same
`App → OpenFileControls/load_example/load_opened → SheetInspector → CellRow → write_and_propagate`
chain), so sequencing avoids both PRs editing the same `inspector.rs` regions concurrently.
#194 also touches `adam-rs/src/sheet.rs` (`add_requirement`, dropping the `name` parameter);
doing this after Group 1's `sheet.rs` `propagate()`/`execute_plan` refactor avoids incidental
conflicts in the same file, even though the touched functions don't overlap directly.

## Group 4 — cel-parser/cel-runtime language surface (independent of Groups 1–3)

**Issues, in landing order:** #110 (arrays and method-call syntax) → #10 (first-class
functions) → #111 (geometry and affine-transform value types)

**Why grouped/sequential:** all three land in the same core parser/runtime files
(`cel-parser/src/lib.rs`, `op_table.rs`, `cel-runtime`'s segment/value-type machinery), so
they're sequenced as one track to avoid conflicting rewrites of the same op-dispatch and
grammar code. #111 has a hard dependency, stated in its own issue text: it needs method-call
syntax (clamping operations on point/size/rect/`TranslateScale`) from #110. #10 (first-class
functions) has no stated dependency on #110, but shares enough surface (op-table overloading,
grammar entry points) that sequencing it between #110 and #111 avoids a three-way conflict;
it could equally be reordered first if that better matches whoever picks up this track.
Fully independent of Groups 1–3 (different crates entirely — no shared files with `adam-rs` or
`begin`).

## Group 5 — adam-lang: equation-style relationship declarations (independent)

**Issues:** #29

Confined to the `adam-lang` crate (parser/AST) and, per the issue's own open questions, an
`OpLookup`-style registry design decision. Has no file overlap with Groups 1–4 and can proceed
in parallel with all of them, though its open design questions (named-equation registration,
symbolic direction inference) may want resolving before implementation starts.

## Group 6 — CEL language book (independent)

**Issues:** #211

A new book crate (e.g. `cel-lang-book`) plus CI/docs wiring, entirely additive. No code in any
existing crate needs to change to add it (aside from `Cargo.toml` workspace `members` and CI
YAML). Zero file overlap with any other group; can start immediately and run fully in parallel.

## Group 7 — begin: `graph.js` unit tests (independent)

**Issues:** #65

Confined to `begin/assets/graph.js` and new JS test tooling (e.g. Vitest/Jest) plus CI wiring.
No Rust file overlap with any other group, including Group 3's `adam-web-ui`/Dioxus changes
(different files: `inspector.rs`/Rust vs. `graph.js`/JS). Can start immediately and run fully
in parallel.
